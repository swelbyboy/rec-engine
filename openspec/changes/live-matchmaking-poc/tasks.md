## 9. Match Quality Fix — Candidate Pool Was Never Filtered by Relevance

- [x] 9.1 User ran the live pipeline against a real role ahead of Task 7 (LightWork AI, Platform/Backend Engineer, `job_order_id` 1650) and flagged the output as wrong: 100 candidates considered, 0 eliminated, top-ranked candidates had no Node.js/NestJS/LLM-agentic experience despite those being extracted as "Rigid" hard constraints. Root cause: `run_live_pipeline` called `live_data.fetch_candidates(limit=100)` with no filter and no `order` clause — Supabase/PostgREST's default row order is by `candidate_id`, so the "pool" for every role was an arbitrary slice of the first ~100 rows of the entire 17,647-row `app.candidates` table, unrelated to the role's discipline or required skills.
- [x] 9.2 Built `src/candidate_index.py`: a persistent, one-time (then incrementally refreshed) embedding index over the entire live candidate table — precomputes each candidate's search-text embedding (reusing `store.candidate_to_search_text`, previously only used by the synthetic-fixture path) AND a per-constraint embedding (feeds `constraint_engine.py`'s semantic-matching phase). Content-hashed per row so a rebuild only re-embeds changed/new candidates. `python -m src.candidate_index build` — first run indexed all 17,647 candidates in ~95s; safe to re-run periodically (Mothership refreshes hourly). `data/live_index/` (real candidate PII) added to `.gitignore`.
- [x] 9.3 First pass wired embedding-similarity retrieval (`retrieval.py`, already existed but was unused by the live path) in as a pre-filter ahead of the constraint engine. User correctly challenged this: it narrows the candidate universe via a fuzzy topical-similarity heuristic *before* any hard constraint is checked, which can exclude a genuinely qualified candidate whose free text just doesn't embed close to the JD wording — the same class of failure as 9.1, one level down. Revised per 9.4.
- [x] 9.4 Extended `constraint_engine.run_constraint_engine()` with optional `employer_embeddings`/`candidate_embeddings` params (keyword-only, backward compatible — existing tests and the synthetic-fixture path call it unchanged) so it consumes precomputed embeddings instead of making a live OpenAI call per candidate; added `embed_constraints()` helper. Rewired `run_live_pipeline()` so hard-constraint filtering runs over the **entire** indexed candidate universe on every call — a candidate is only excluded for failing an actual constraint. Embedding-similarity retrieval now applies only *after* hard filtering, solely to cap the pool sent into the fine-rerank LLM call when it exceeds `rerank_limit` — never to decide compatibility. `candidate_limit` is now optional/dev-only (`None` = scan everyone, the correct default for real use); UI no longer sends a hardcoded value.
- [x] 9.5 Added a complementary signal: `scoring.skill_match_detail_batch()` (batched call, reuses the existing embedding-based `skill_coverage()` matching from the unused weighted-linear path) computes each candidate's matched/missing required+preferred skills once per rerank, surfaced explicitly in `fine_rerank`'s candidate blocks and referenced in the system prompt — so verdicts are grounded in an explicit skill-fit signal rather than inferred from free text alone.
- [x] 9.6 Re-verified against LightWork AI (`job_order_id` 1650) and Ankar AI (1360) with the 9.1–9.5 fix as committed to the working tree (before any of section 10's changes). Both came back sensible: LightWork's top 3 carried 12-13/15 required skills, Ankar's top 2 carried 5-6/6 — no repeat of the original bug. `candidates_considered` was 17,660 for both (full universe, confirming 9.1's arbitrary-100-row-slice bug is gone). The user separately shared an "100 considered / 8 passed filter" Ankar AI screenshot that looked like a regression — traced to a stale pre-9.4 run (the UI used to hardcode `candidate_limit`; 9.4 removed that), not a new bug. The real gap this surfaced: `candidates_passed_filter` was 1,762 (LightWork) / 3,344 (Ankar) but only 30 ever reached the fine-rerank LLM (`rerank_limit` default), chosen by embedding similarity rather than real judgment — see section 10.

## 10. Scale the fine-rerank stage past its ~30-candidate ceiling

User asked to run fine-rerank over a much larger pool and pointed at Mind's own production rerank (`mind/apps/web/src/lib/reranks/`) as the reference — read it in full before implementing, ported what's valuable for this PoC, explicitly left out what's Mind's own production-hardening (see `openspec/changes/live-matchmaking-poc/poc_context.md`-adjacent design discussion for the full port/no-port breakdown).

- [x] 10.1 Confirmed `SKILL_FLOOR_RATIO` (0.4) didn't need raising given fresh 9.6 evidence — left as-is, documented inline in `funnel_rerank.py` why.
- [x] 10.2 Populated `Candidate.discipline` from `app.candidates.title_families` (`live_data.py`) instead of hardcoding `"other"` — Mothership's own taxonomy already matches rec-engine's `Discipline` enum values exactly.
- [x] 10.3 Added `title_embedding` to `candidate_index.py` (current + recent previous titles, separate `.npz`, same incremental content-hash pattern) and `_apply_title_relevance_check` in `funnel_rerank.py` — a lenient, title-text-only embedding gate (deliberately narrower than `retrieval.py`'s full JD-vs-bio similarity) that eliminates only extreme discipline mismatches. Ran a full-index rebuild with `--force` since the discipline/title fixes live inside cached `Candidate` blobs the incremental path wouldn't otherwise touch.
- [x] 10.4 Added `FINE_RERANK_MODEL` (`claude-sonnet-5`) for the fine-rerank stage only — `models.py` previously had a single `LLM_MODEL` (Haiku) used for extraction, coarse brief, *and* fine-rerank; Mind's own reasoning ("Haiku's confidence isn't calibrated enough for a fine score") applies directly here, since fine-rerank's verdict/rationale is exactly what a recruiter judges quality by.
- [x] 10.5 Chunked `fine_rerank()`: fixed `RERANK_BATCH_SIZE` (40, reused from the prior single-call default) instead of a `max_tokens` formula that saturated Anthropic's output ceiling around ~32 candidates; calls run serially per chunk (mirrors Mind's `RERANK_CONCURRENCY = 1` — concurrent long streams starved the event loop in their production incident). Added `_merge_ranked_batches` (verdict-tier + skill-coverage-count merge — valid without Mind's absolute-score rubric redesign, since the verdict is already a fixed-criteria judgment, not batch-relative) and a missing-candidate fallback (flagged `weak_match` rather than silently dropped). Added `_strip_lone_surrogates` (real candidate free text occasionally contains a lone UTF-16 surrogate that breaks the whole API call's JSON encoding), prompt caching on `FINE_RERANK_SYSTEM` (pays off now that a run makes several chunk calls), and a single retry per chunk.
- [x] 10.6 Added `triage_candidates()`/`select_by_coarse_bucket()` — cheap Haiku bucketing (strong/maybe/no) ahead of fine-rerank, triggered only when the filter-passed pool exceeds `TRIAGE_TOP_N = 100` (Mind's own cutover threshold, reused directly). Unbucketed/failed-chunk candidates default to "maybe" — a triage failure degrades to "keep everyone," never drops the pool.
- [x] 10.7 Repurposed `rerank_limit` from "must fit in one call" to a sanity ceiling on total candidates entering the now-chunked rerank stage; raised default 30 (UI) / 40 (backend) → 200 both places, and stopped `LivePocPanel.tsx` hardcoding `rerank_limit: 30`. Order is now: hard filters (uncapped) → triage (if pool > 100) → embedding-similarity trim (only if still above `rerank_limit`, last resort) → chunked fine-rerank.
- [x] 10.8 Added unit tests (`tests/test_funnel_rerank.py`): merge by verdict-tier + skill-coverage tiebreak, missing-candidate fallback, dedup-on-duplicate, coarse-bucket selection (best-nonempty-bucket, unbucketed-defaults-to-maybe, all-"no"-still-forwards, top_n cap), and title-relevance gate (elimination + missing-embedding passthrough, via a monkeypatched embedder so these stay fast/pure).
